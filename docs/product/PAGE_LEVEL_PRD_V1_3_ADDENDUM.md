## 一、公共产品规则

1. 产品向用户提供的是**需求画像和养老机构初步参考**，不做医疗判断，也不承诺机构具备全部照护能力或必然接收。
2. 关键风险明确、机构相应能力全部未知时，**仍允许成为“初步参考候选”**，前提是有真实可解释的非护理参考依据（如地区、预算、基础服务范围），且不存在已知明确关键能力冲突。
3. 参考候选必须高可见度标识“初步参考 · 关键护理能力待核实”；不得转换成 Exact、SoftNear、Conditional 或安全匹配已通过。
4. 用户如实填写的情绪波动、吞咽不顺、走失风险，不得因缺少核实资料而被要求修改为不真实的正常答案。
5. 个性化结果区域最多三家；没有足够依据时展示普通机构目录入口，而非伪造个性化理由或强行补满三家。
6. 现有机构真实性、历史快照、正式/演示隔离、账号授权和通信 Gate 均保持。

## 二、页面 09 老人需求画像

**路由：** `/pages/assessment/profile`  
**对应原文档：** MVP 第 11 页相关页面规则，PRD 中老人画像章节。

### 展示规则

- 信息分为“已填写事实”“系统理解的需求”“需要后续核实”，不得混成单一未通过状态。
- 情绪波动、吞咽、走失、专区需求应独立展示：走失风险并不自动等于已决定入住认知症专区。
- 待核实项允许标注来源、事实和下一步机构核实；不强制用户循环修改原有答案。
- 画像中的风险提醒不能被其他橙色标签淹没；在 320／375／430px 与系统大字号下应保持可读。

### 交互规则

- 完整问卷无论是否存在待核实事项，均可进入下一步查看参考结果。
- 若问卷仍缺少契约要求的题目，按原校验规则处理，不冒充问卷完成。
- “返回修改答案”和“保留答案、继续查看参考”是不同动作；后者不修改 Assessment。
- 如未来增加补充事实字段，需经后继契约定义来源与清理规则；本次不要求增加原问卷题目。

## 三、页面 10 评估结果与机构推荐

**路由：** `/pages/recommendation/result`  
**对应原文档：** 页面级 PRD 第 17 页、MVP 第 12 页。

### 输出区块

1. 当前画像中最重要的已知需求与真实风险。
2. 本次状态：已核实匹配、条件匹配、初步参考、暂无个性化候选。
3. 最多三家候选，每卡区分“为什么列出”“哪些资料未知”“需要向谁核实”。
4. 无候选时的原因与机构目录／咨询入口。
5. “保存本次评估”及“查看我的评估”入口（正式身份绑定完成后才可真正保存）。

### 初步参考候选卡最低元素

| 元素 | 展示要求 |
|---|---|
| 状态 | “初步参考 · 关键护理能力待核实”，不能弱化成浅灰角标 |
| 参考依据 | 仅来自已知真实的地区、预算、机构基本服务等条件 |
| 待核实事项 | 明确与老人风险相关的未知护理能力，逐项可读 |
| 操作 | 查看机构当前资料、咨询机构／顾问以核实能力 |
| 限制说明 | “是否具备相应照护条件及能否接收，须由机构核实确认” |

### 结果分组与入口准则（Owner 2026-10-26 已确认）

- 先保留现有可展示的 Exact／SoftNear／Conditional 及原排序；这些结果存在时不以初步参考补满三家。
- 旧 V2 无可展示卡片时，独立计算参考资格。至少一项真实、与当前老人明确需求对应且证据有效的普通匹配依据：指定区域匹配、可比口径的费用区间重叠、已核验的普通服务偏好。只有机构在武汉、仅有名称地址、VR 图片或模糊报价均不能算依据。
- 与老人必要关键照护能力存在明确已知不支持事实的机构不进入个性化候选；机构相关能力未知则逐项显著提示，不能标“适配已通过”。
- 独立参考卡仅按可信普通依据形成可解释次序，不显示护理适配评分；卡片不超过三家、不重复同一机构。依据类别数与稳定机构 ID 的具体 tie-break 属待技术审查细节。
- 没有参考依据时保留普通目录入口；数据错误／身份失效／服务故障不使用“无合适机构”的空态。

**禁止**：以风险能力 `unknown` 加分，标记“安全匹配”，出现无依据的匹配百分比，或将 Demo 合成资料显示为正式能力核实。

### 三个典型场景

| 场景 | 预期 |
|---|---|
| 有吞咽不顺，机构能力未知，其他普通条件有依据 | 可显示“初步参考”；吞咽相关能力明确待核实 |
| 有走失风险，机构明确无相应保障能力 | 从该老人个性化候选排除；普通目录按合法规则独立处理 |
| 风险明确、能力未知，而且没有可信的地区／预算／基本服务依据 | 不构造个性化候选；提供普通目录及咨询入口 |

## 四、页面 21 我的评估

**路由：** `/pages/assessment/history`  
**对应原文档：** 页面级 PRD 第 42 页、MVP 第 23 页。

### 首期范围

- Owner 确认**先完成单老人正式历史闭环**：合法绑定的当前老人可保存、查询、打开当次评估与推荐。
- 多老人管理作为后续独立阶段，不在本次交付中以绕过老人权限的方式实现。
- 允许保存“本次没有推荐候选”的评估，历史页应完整显示原因。
- **Owner 已确认方案 A**：查看结果不会自动写入历史。由用户明确点击“保存本次评估”启动可信保存流程；收到成功回执后才能显示“已保存”。

### 保存按钮和身份状态（显式保存产品方向已确认，异常状态细节待技术审查）

| 状态 | 结果页或历史页需要表现 |
|---|---|
| 仅预览 | 标注“本次评估尚未保存”；退出不产生正式历史 |
| 未登录／未合法绑定当前老人 | 点击保存后引导所需授权；不自动保存、不将关系答案当授权 |
| 保存中 | 按钮防重复，必要时保持同一操作意图 |
| 结果已变化 | 重新展示发生变化的结果并要求再次确认；不得静默保存 |
| 超时／回执不明 | 告知待核对并安全重试；不显示成功、不生成第二份 |
| 保存成功 | 展示可信完成时间和“查看我的评估” |
| 保存后继续修改 | 原历史记录不变，新变化标未保存；再次明确保存生成另一条 |

正式历史至少区分空列表、未开放、无授权、网络失败及不支持的旧快照。不得在匿名浏览或结果页自动展示时提前上传完整健康答卷。

### 历史列表与详情

- 历史按保存时间倒序；每条明确日期、老人、状态及是否有候选。
- 点击记录查看当次画像和当次推荐快照；旧版本无法显示时明确说明，不补算。
- 如果历史记录有关联机构，区分“当次保存的资料”和“查看目前的机构资料”；不能悄悄替换旧快照。
- 认证过期、无当前老人绑定、缺少授权时给出真实的登录或绑定引导，禁止读取其他账号数据。
