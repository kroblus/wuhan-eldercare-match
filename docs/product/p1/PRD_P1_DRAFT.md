## 1. 范围与来源

S1—S6为此前商业愿景、机构手填表及简介；S7为本轮《柠月颐养中心入住价格公示表（2026年）》；S8为用户本轮对范围、电话、标签、后台及带看流程的明确说明。采用新说明修订旧建议，不把旧商业愿景中的年费与佣金继续列为软件功能。

本轮核对GitHub分支`codex/unified-source-baseline` HEAD仍为`186a46517459e7d5080bc62b22ebaab51c0add62`。C1和C2-A已有成果沿用先前证据，本轮无业务复测。完整旧问卷32项/26必填与轻量新输入分版本，不能补造旧答案。

**核心边界：** 平台免费咨询和对接，不代表养老机构入住免费；线下签约不进软件。机构收费只作信息展示/预算参考，不构成支付订单。默认一个朋友运营账号、一个后台，不建机构商家端。

## 2. 机构资料：人工确认结果进入系统，不造签约审批

保留院区稳定ID、展示名称、机构性质、区域、详细地址/入口、照片、服务时间、接收说明、展示标签、价目表、公开状态及简单更新时间。朋友负责现场核对；未现场确认不能提前把核对日期填为今天。机构性质按确认值录入，原民办非营利勾选是来源，不自行作登记法律鉴定。

不设计合同主体、签约收款主体、合同版本、年费期限、佣金和续费管理。机构必须有正确地址供实际看院；“朋友线下核实”不等于软件不用地址。原个案中未提供的实景、VR、短住日价不补造。

### 2.1 咨询号码

朋友可以为多家机构担任同一平台顾问。配置一次平台顾问身份/公开号码，可按机构关联，不把号码散落在多张卡中硬编码。

面向用户标注“平台咨询”“预约咨询”或“专属顾问”；详情说明由平台顾问协调机构与家属。机构官方电话是另一个可选来源，不能把朋友号码复制进officialPhone字段后称官方。朋友实际号码尚未在本轮给出，由后台/本地合法配置补入，不从早前表中任取一个个人号码代替。拨号按钮沿用合法校验、防重和错误反馈。

### 2.2 展示标签与护理判断分开

“医养结合”可按用户要求成为首页卡片展示标签；后台记录标签原文、来源和确认说明，详情注明“服务特色据机构介绍，具体服务请咨询”。不把标签推导成有医疗机构执业许可、院内医务室、24小时医师、医保报销、专业康复治疗或特定护理接收保证。展示标签字段不直接作为安全匹配通过依据。

用户口述“说好康养和短期脱亚”暂按上下文整理为“术后康养、短期托养”。记录为朋友确认可提供的服务方向，录入时确认最终标签用词；不继续把旧表未勾选当否定，也不扩大成医疗康复资质。认知/吞咽/管路等具体接收条件仍独立。

## 4. 用户需求：为了服务和统计，不为了收集而收集

公开浏览无问卷前置；普通咨询和看院可先提供最小联系信息、目标机构、意向时间。联系人只在主动提交服务请求时收集，匿名输入不自动上传健康资料。朋友代填标注代填来源及本人确认情况，不能把线下填报伪装成小程序自然获客。

轻量需求建议8组：服务场景（长期/短托/术后阶段/未定）、可接受区域、入住时点、常规月预算、年龄段/代填关系、行动转移/吃饭/如厕帮助、需要提前核实的情况、老人意愿与少量偏好。短住再问日期和天数；专业细节只在有用途时补问。

照护分布来自“用户自述/顾问核实”，与S7的五档收费等级严格分开。可统计生活自理程度、认知/走失、吞咽、夜间帮助、管路/伤口、长期/短期等；不同风险可重叠，报表要说明多选总数可能大于需求数。允许不清楚/不愿细填，不将未知归为正常。

## 5. 网页控制面板（内部，不是机构自助后台）

| 页面 | 朋友日常操作 | 必要结果 |
|---|---|---|
| 工作概览 | 看待联系、待安排、今日带看、待回访及当期真实数量 | 可以直接跳到对应记录，不做无用大屏 |
| 老人需求 | 按日期/来源/区域/预算/照护需求/机构/状态筛选；查看摘要、联系、备注和下次动作 | 当前跟进负责人和更新时间明确，身份无权时不得返回记录 |
| 带看日历 | 日/周视图及待安排列表；选择时段、改期、取消、完成 | 看到冲突与交通缓冲，保存以服务端回执为准 |
| 机构资料 | 编辑性质、地址、特色标签、价目表、公开内容、平台电话关联 | 能维护第一家及后续少量机构，不要求全字段齐才录草稿 |
| 报表中心 | 选择日期、机构、来源和统计类型；预览；导出Excel | 查询和导出同一筛选/快照，外部汇总不带内部明细 |

网页通过已鉴权的后端API查询数据库，不把MySQL凭据放浏览器，不允许页面直接连数据库。优先同仓简单Web前端和现有Spring Boot/MySQL，不建数据仓库、微服务、独立BI服务、通用规则平台。首期一名管理员即可，后续真有协作者再增最小权限角色。

## 6. 带看：申请不是预定，安排必须核对冲突

### 6.1 用户申请

记录目标机构（可为空表示请顾问推荐）、联系人及合法联系方式、候选日期/时段、参加人数、需提前说明的出行协助（选填）。可提交多个备选时段。提交成功提示“带看申请已提交，顾问联系后确认具体安排”，不立即占用机构床位、不显示预约已确认。

不用强迫用户先交完整病史；看院本身不等于入住接收评估。电话点击只记录咨询意向事件，不证明电话接通或服务申请成功。

### 6.2 朋友安排

最小流程：待联系/安排 → 沟通中 → 已确认安排 → 已到访/已取消/未到访。改期可作为既有安排上的操作，不为此新造庞大状态机。时间需开始/结束、机构、集合地点、带看负责人以及双方确认情况；服务时间统一Asia/Shanghai。

首期朋友默认是带看负责人；机构联系人只作内部安排使用，不因录入而公开。一个家庭看多家机构时分别记录看院事件，家庭需求仍是一个；甲机构取消不取消乙机构看院。

### 6.3 时间冲突规则（建议实现）

- 待安排申请可以重叠；不能因为其他家庭也选周六上午就拒收需求。只有正式确认/保留的排期占用对应资源，首期不必实现自动短暂占位。
- 同一带看负责人不能同时执行两场不同带看；同一家庭的已确认行程也不得重叠。工作人员个人不可用时段可手工登记。
- 机构如果明确限制同一时段接待组数，才应用对应容量；不同家庭同院看院不应无依据地一刀切禁止。首期不预建机构排班系统。
- 增加可调交通/准备缓冲，由朋友填写或设置默认值；默认分钟数为实施时展示给用户的可调建议，不宣称系统已算出路线耗时。无需地图智能调度。
- 用半开时间区间，冲突为newStart < oldEnd且oldStart < newEnd；先纳入各记录缓冲。相邻行程在无缓冲时可接续，有缓冲则检查后再确认。
- 前端选择时提示冲突；后端提交时在一个事务内重新核对并写入。确认/改期对同一负责人排期采用数据库锁等现有最小手段，避免双标签页同时成功。不要只靠前端提示。
- 改期先验证新时段，验证失败保留旧安排；成功后原子替换。取消释放未来时段，日期过去不自动标“已到访”。后台刷新失败不显示“已安排”。

示例（合成）：朋友周六10:00—11:00已安排A院，交通缓冲30分钟；10:30—11:30或11:00—12:00的新确认应提示冲突，11:30起是否可约还需双方确认。两个待安排申请都写“周六上午”可以同时保留。

用户看到本人申请的当前状态，改期后显示新时间；没有消息通知接入时不宣称微信通知已经发送。工作人员需向双方确认，可记录确认结果。

## 7. 获客报表与漂亮Excel

### 7.1 报表的两种用途

**外部：机构获客与服务汇总。** 默认聚合且不包含可识别个人信息，用于展示平台带来的需求、实际对接与到访成果。不包含姓名、完整或部分电话、精确住址、身份证、具体生日、自由文本病史/备注、恢复意图或账号凭证。小样本敏感组合可能识别人，改为更粗分组/隐藏敏感交叉表，不机械认为打码就匿名化。

**内部：跟进明细。** 仅朋友等有权限的工作人员查看/必要导出；包含联系状态、需求摘要及待办，标“内部使用”。具体机构确需接收某个案例时，只按该个案获准目的和范围提供最小资料，不把全库健康名单发给所有机构。

两类导出分开入口和文件；不能把内部明细藏在对外Excel的隐藏sheet。生成外部报告直接从聚合查询构建，不先导出全量再隐藏列。

### 7.2 统计口径

| 指标 | 定义/限制 |
|---|---|
| 访问人数与浏览次数 | 区分UV/PV及可实际取得的统计口径；没有访问埋点不能造数字 |
| 新需求 | 成功创建的正式ServiceRequest/NeedIntake，重复点击与重试按同一意图去重；不自动叫不同老人总数 |
| 可联系/已联系 | 有合法联系方式与用途；已联系需朋友记录实际结果，拨号按钮点击不算接通 |
| 机构关联需求 | 明确选择或由顾问关联该机构；平台全部需求不能归到每家机构 |
| 带看申请/已确认 | 按对应阶段记录；确认不得从用户意向时间推导 |
| 到访家庭/到访人次 | 去重家庭/需求数与事件数分开；一家看两次是两次事件但不是两条新家庭需求 |
| 后续入住反馈 | 只记录有来源的家属/机构/顾问确认，不等于签约功能或收入；未知单列 |
| 渠道来源 | 小程序入口、社区活动、转介绍、线下人工录入分别标注，保留未知 |
| 护理需求分布 | 自述/顾问核实的日常帮助、风险与服务场景；未填写单列，多选不要求合计100% |

报表显示统计时间范围、生成时刻、机构范围、筛选条件、时区与口径版本。以同一数据快照生成页面与Excel；生成中状态变化不使页签数字各自不一致。测试、Demo、员工自测不计真实获客。

期间活动报表展示各事件按发生时间的数量；转化率必须使用同一批需求的队列，并写分母和观察截止日，不能用本月到访除以本月新需求冒充转化。同一需求可关联多机构，平台去重总数不能简单相加各机构数。没有稳定老人/家庭身份时明确用“去重需求数”，不从同手机号自动推断同一老人。

### 7.3 首版Excel格式

1. 报告总览：平台/目标机构名称、统计周期、来源口径、关键数据卡、少量图表、真实服务范围说明。
2. 需求画像汇总：预算档、区域、年龄段、服务场景与照护帮助分布；只用已允许的聚合粒度。
3. 机构服务漏斗：机构关联需求、联系、申请、确认、到访、后续反馈；数量与转化分母并列。
4. 统计口径：统计条件、未知/排除项、去重方式、来源区分、生成时间和更新说明。

沿用亮橙色强调、深色文字、足够留白；统一标题、数字单位、百分比小数位、冻结表头、合理列宽、打印页眉/页脚和横向分页。缺数据写“未采集/暂无”，不是伪造0或演示数据。文件名包含机构、统计区间、生成日期，不含老人姓名电话。原始字符串按文本处理，不执行用户输入的Excel公式。首期标准XLSX优先，打印版/PDF按实际需要补，不建另一个报表平台。

## 8. 数据和权限的最小边界

建议对象：Institution/DisplayTag/PriceSchedule、NeedIntake、ServiceRequest、VisitAppointment、FollowUp，少量统计事件或现有时间字段；ReportExport只记录导出人、范围与时间。报告来自同一业务数据库，不复制成Drive客户表。

匿名浏览、请求联系、健康信息保存和向具体机构提供资料的目的分别说明。真实健康数据和可识别个案分享需适用的合法依据、告知与同意；不能因为免费或称公益就忽略。法律参考：个人信息保护法第6、17、23、28—30条；这是产品边界提示，不是合规认证。

后台接口强制工作人员身份；用户接口核对本人/合法代办范围。普通用户即使知道后台URL也不能查库或导出。费用、标签编辑和导出留必要操作者记录即可，不设多级审批。真实客户数据、电话号码与健康答案不进入GitHub、Codex日志或开发Drive。

## 9. 定向验收（按任务范围选择）

1. 公示五档总价与各分项一致，最高7200，不再显示旧7000；床位费和总费不混用。
2. 医疗备用金、床品、伙食费分别展示；不自动承诺退款或短托日价。
3. 平台咨询拨给配置的朋友号码，身份不写“机构官方电话”；无实际号码时不可假拨。
4. 首页可展示医养结合，但护理资格判断不因该标签自动通过。
5. 不填完整旧问卷仍可浏览和发起普通请求；不造旧必填答案。
6. 真实提交可在后台查到，同一意图重试不重复；Demo数据不进入真实列表。
7. 重叠的意向时段可同时进入待安排，非自动预约确认。
8. 同负责人/同家庭已确认排期冲突被提示并在服务器拒绝；并发确认不能双成功。
9. 有缓冲时检查有效占用；无冲突的相邻行程可排；取消释放时段。
10. 改期冲突失败不丢旧安排；实际到访由明确反馈记录。
11. 未登录、普通用户、其他家庭不能查询后台或越权导出。
12. 单机构报表仅计关联该机构记录；多机构求和不冒充平台去重。
13. 访问/点击/申请/确认/到访分别统计；线下人工、测试、未知来源各自标清。
14. 外部Excel包含汇总与口径，不含隐藏客户页、个人号码和病史；小样本合理合并。
15. 后台预览和导出同筛选/快照一致，风险多选和未知项口径可解释。
16. 小程序和后台均没有合同、支付、佣金、结算或平台收费入口/数据表。

## 10. 尚缺但不阻塞独立编码的资料

朋友实际公开号码；最终“术后康养”用词、短住日费/期限；医疗备用金使用/退还和床品计费条件；朋友现场确认后的院区入口；工作时段和交通缓冲；真实个人信息告知/合法代办与保留办法。以上相关发布或真实使用前落实，其他界面、API和合成测试继续做，不再征询已排除的收费/佣金参数。
