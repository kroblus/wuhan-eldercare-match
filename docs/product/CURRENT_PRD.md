## 1. 数据模式：先分清页面展示的是什么

| 模式 | 数据和行为 | 对用户如何说明 |
|---|---|---|
| Demo 演示 | 图册预置 12 家虚构机构、2 位虚构老人；记录在隔离内存会话；顾问回复、预约、带看是本地模拟 | 明示“演示/虚构”；模拟保存不表示正式历史，模拟预约不联系机构 |
| 正式机构目录与预览 | 当前资料可用于浏览；10-26 审计记录有 11 家正式目录，但关键护理能力缺少核验资料 | “收录资料”不等于合作关系、护理能力已通过或机构愿意接收；数量是带日期的数据状态 |
| 正式个人记录与服务 | 需要真实身份、老人关联和实际服务端；本材料不能证明已开放 | 未开放就说明未开放，失败就说明失败，不用空列表或演示成功替代 |

机构数量、价格和核验情况会变化，不写成永久产品指标。问卷中的亲属关系和“希望顾问协助”只是用户答案，不等于后台身份授权或允许发出联系。

## 2. 当前功能：用户能做什么、会看到什么

下表按现有实现与适用产品规范整理页面行为；未对每一条重新做运行验收。C1/C2 待实现内容另列。“成功”指相应模式下实际完成的动作；Demo 成功只代表演示会话成功。

| 功能 | 用户操作与正常结果 | 空、缺资料或未开放 | 出错时 |
|---|---|---|---|
| 首页与三个阅读页 | 选择查机构、整理需求、政策、科普或入住指南；阅读页附来源与核对日期 | 没有相关内容就说明资料不足，不给出个人补贴资格或医疗判断 | 给出返回/重试入口，保留已完成问卷 |
| 六步需求评估 | 填写基本、健康、日常能力、认知护理、偏好、预算；核对画像并按模块修改 | 不确定可保留；必填未完成时定位到相应题目 | 保留合法输入，不要求重填整份问卷 |
| 画像与当前结果 | 看到需求、风险、候选理由和待确认事项；继续看详情或普通目录 | 零候选说明原因，仍可浏览目录；预览不自动保存 | 资料或服务错误单独说明，不能写成“没有合适机构” |
| 普通机构目录 | 搜索名称、按区域和性质筛选，再看资料 | 没有搜索结果时允许调整条件 | 资料加载失败可重试；目录不是个性化排名 |
| 机构详情与 VR 资料 | 带机构 ID 和版本查看资料、来源、联系方式及合法资源 | 未核验、过期、不可用各有说明；没有有效参数显示链接无效 | 返回目录或重试；不以旧或虚构资料冒充当前机构事实 |
| 顾问与 FAQ | Demo 顾问提供本地示例对话；FAQ 回答已批准的通用问题 | 没有答案就说明无法回答；真实顾问服务不可用时如实提示 | 保留问题和可用返回入口；不能宣称已经联系真人 |
| 看院安排与申请结果 | Demo 体验模拟安排；有效一次性回执才可展示该次结果 | 没有机构上下文、回执或服务能力时分别说明 | 不伪造成功；可信受理也只代表申请提交，不代表机构确认 |
| 我的、老人档案与评估历史 | Demo 查看虚构老人及当次只读快照；由记录进入相应详情 | 无记录、服务未开放、无授权、旧快照不支持需分别说明 | 加载失败与没有记录分开，不用当前资料静默补算历史 |
| 看院评价 | 从已完成的看院记录进入三步表单；已有评价可只读查看 | 缺少有效看院记录时说明入口问题；选填项可空白 | 保存失败保留输入；不得冒充已保存 |
| 演示控制台、地图与合成全景 | 载入/重置演示案例；看城市底图或合成空间 | 未载入可提示载入，资源不可用可返回 | 可以重试；城市底图不代表真实院址，合成全景不代表机构实景 |

### 问卷与评价的当前口径

现行 Assessment V2 是 **32 项，26 必填、6 选填**，分六步；日常生活能力仍为七项。历史 27/21 口径不可用于本分支。未知答案保留，不从吞咽不顺推导鼻饲，也不把走失风险自动变成认知症专区需求。

当前评价分“总体体验 → 现场观察 → 最后确认”。包含总体印象、后续考虑意向、21 个可选分项评分、护理管理观察、费用解释、最多各 3 个满意/担心标签和最多 200 字补充。费用清晰度当前采用清楚/不清楚及分项说明，不是旧 PRD 所写的评分项。本文件只说明现状，不改变存储字段。

### 当前咨询能力的准确说法

养老咨询助手目前使用预先批准的 FAQ，图册明确没有在线模型，也不读取本次画像、推荐和机构上下文。V1.2 的“解释已有画像与推荐”是保留目标，不能列为已经完成。真正接入在线模型时，由后台调用，前端不存模型密钥；AI 不重算推荐、不报价、不写机构事实。

机构官方联系方式和平台顾问联系方式分别展示。旧产品已经允许未来增加独立的机构官方电话；需要继续保持身份真实，不能把平台号码换个标题充当官方号码。

## 3. V1.3 已确认方向：仍有待实现的页面行为

### C1：让家庭得到诚实的初步参考

现有合法核实型候选存在时，保持旧结果与顺序，不为了补满三家加入参考候选。旧通道没有可展示候选时，才走独立 C1 通道。

参考资格至少来自一种与老人明确需求对应的可信依据：指定区域匹配、可比月总费用区间重叠、已核验房型或餐次偏好。只有名称、武汉地址、照片或宽泛“医养结合”宣传，不构成个性化依据。必要关键护理能力存在明确冲突时仍排除；能力未知可以保留为显著待核实事项，不能写成“适配通过”。

每张参考卡应让用户直接看懂四件事：**为什么列出、哪些能力未知、下一步向谁核实、这不是接收承诺**。最多三家，不显示没有依据的护理匹配百分比。没有可信依据时提供普通目录，不强行补数。

**当前状态**：C1-A 与 C1-B 页面接线已实现并通过定向自动化；手机验收尚未完成。独立 ViewModel 只映射组合快照，不重新判断资格或排序；参考卡以精确机构版本进入公开详情，保留护理未知及全部重要风险，不触发正式保存。C1 的精确依据、排序与饮食冲突规则见 [独立 C1 契约](../architecture/INITIAL_REFERENCE_RECOMMENDATION_CONTRACT_V1_3_C1.md)，早期产品稿的宽泛举例不能扩大该范围。

### C2：先完成一位老人的正式历史

用户查看结果时先预览。只有主动点击“保存本次评估”，完成必要身份与老人关联并得到可信成功结果，才显示已保存。没有候选的结果同样允许保存。

保存中避免重复触发；超时或回执不明时说明待核对并允许安全恢复；若拟保存内容已变化，展示变化后再由用户确认。保存后继续修改产生未保存的新变化，不覆盖旧历史。历史显示当时画像、结果与资料版本，当前机构资料通过单独入口查看。

**当前状态**：正式后端与完整读写闭环仍未开放。首期按已确认决定只做一位合法绑定老人的闭环，多老人是后续范围。Demo 两位老人不改变这一范围。

已确认产品依据见 [V1.3 决策](RECOMMENDATION_AND_HISTORY_PRODUCT_RULES_V1_3_DRAFT.md)、[页面补充](PAGE_LEVEL_PRD_V1_3_ADDENDUM.md)和 [流程补充](MVP_PAGE_FLOW_V1_3_ADDENDUM.md)。其中早期“C1 尚未实现”应结合后来的 C1-A 实施报告理解。

## 4. 日常开发保持简单

在同一个主项目内继续迭代。按本次需求读取相关页面、适用规则和最近一份阶段总结，完成后更新进度入口。小范围文案、样式或布局调整，不自动新增技术评审、冻结文件或全项目测试轮次。

若改变推荐语义、正式保存、账号权限或机构事实，说明具体行为差异并做相应验证；已有用户授权不重复索取。业务规则保留，文档流程尽量短。正式后台、在线模型、公开评分、支付和复杂多老人管理，不因整理页面而自动加入本次范围。
