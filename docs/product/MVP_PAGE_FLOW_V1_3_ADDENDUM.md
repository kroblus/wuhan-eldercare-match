## 页面 09 老人需求画像

**用户要解决的问题：**“系统有没有正确理解老人的情况？如果存在还需机构核实的事项，我能不能继续了解机构？”

展示内容：

- 老人已报告的健康、生活能力、认知、进食、偏好、预算等事实。
- 单独突出走失、吞咽不顺等重要风险，以及专区需求是否明确。
- 把“我需要补充的信息”和“需要机构确认的条件”分开。
- 保留逐模块修改入口；用户不必为继续查看参考结果而更改真实答案。

主要操作：**查看机构参考结果**。问卷完整即可继续；是否展示个性化候选由下一页分级说明，未完成必要题目仍保留原校验。

## 页面 10 评估结果与机构推荐

**用户要解决的问题：**“根据已经填写的信息，我现在能先了解哪些机构？哪些事情还必须问机构？”

新增的结果解释：

| 状态 | 用户看到的含义 |
|---|---|
| 已核实匹配 | 机构已核实资料满足既有匹配规则；仍非最终接收承诺 |
| 条件匹配 | 需根据机构既有合法评估条件进一步确认 |
| 初步参考 | 地区、费用等已知条件提供了参考依据，但与老人风险有关的机构护理能力可能全部未知 |
| 暂无个性化候选 | 目前资料不足或存在冲突；仍可查看普通机构目录／咨询 |

**初步参考卡**必须显著显示“关键护理能力待核实”；包括推荐依据、与老人风险相关的未知资料、咨询核实入口。存在已知明确关键冲突时不得以“初步参考”绕过排除。只有名称或地址、没有可信个性化依据时，仅能作为目录浏览，不能算推荐。

页面保留最多三家个性化候选、核心需求突出、差异说明及顾问入口。不得凑数、不因未知能力给出虚假高匹配度。

新增业务动作：**保存本次评估**。Owner 已确认采用方案 A：必须由用户主动点击，完成必要身份与老人绑定并获得成功回执后才算正式保存。即使本次一张候选卡都没有也可保存；仅查看结果不自动保存。

**可见行为补充（准入与展示层级已由 Owner 确认，异常态仍待技术审查）**：

- 存在现行合法核实型卡时优先展示，初步参考不为了凑满三家而混入；完全没有核实型卡时，才从符合明确区域、可比费用或已核验普通服务偏好的机构中给出最多三家初步参考。
- 机构只有地址和名称而没有任何与老人明确需求对应的可信依据时，应显示合法普通目录入口，不能写“推荐给您”。
- 保存按钮区分“未保存”“请先登录／绑定当前老人”“保存中”“保存结果变化需重新确认”“保存情况待核对”“已保存”。若用户看到的结果与服务器拟保存快照不一致，不得默默保存。
- 保存后修改原问卷不会修改历史；需要形成新历史时必须再次主动保存。旧历史不按当前机构能力或新推荐规则自动改写。

## 页面 20 老人档案

既有“管理多个老人”长期目标不取消。本阶段先交付**当前合法绑定的单老人正式历史业务闭环**，多老人切换和跨老人历史浏览进入下一阶段。界面不得将未实现的多老人能力表述为已可用。

## 页面 21 我的评估

**用户要解决的问题：**“我之前保存了哪次评估？当时得到了什么结果？”

- 按保存时间倒序查看当前已授权老人的记录。
- 打开当次评估和推荐快照；当次没有候选时仍可查看原因。
- 可以发起新的评估，不覆盖旧记录。
- 需要看机构详情时，明确区分“当次资料”和“机构当前资料”；旧资料缺失要说明，不用现今资料暗中补填。
- 账号未验证、老人未绑定或授权不符时，显示真实状态和合法操作入口。
- 无记录、后端未开通、无权限、加载失败和版本不受支持均应显示不同提示，不可全部变成“暂无历史”。

## 一个可直接演示的参考流程

1. 用户如实完成六步问卷，包含“偶尔吞咽不顺”和“存在走失风险”。
2. 画像展示风险事实和待机构核实事项，但不要求回去选“正常”。
3. 结果页展示最多三家有真实普通条件依据的**初步参考候选**；每家都提示相关护理能力尚未核实，不保证接收。
4. 用户可查看机构已收录资料、咨询相关问题；不能把未核实资料当作已通过安全匹配。
5. 用户明确保存此次评估，得到成功回执。
6. 从“我的评估”打开该记录，看见当次画像、状态和快照；重新评估则生成新记录。

**与演示版的区别：**上述流程描述正式产品应达到的目标，不代表当前 B1.2.6 Demo 模拟存储已经是正式服务端历史。地图、VR、顾问等仍分别遵守真实／模拟资料标识。

## 本轮产品决策及边界

1. **允许高风险与未知机构能力同时存在的初步参考**，但必须高可见度风险标识、真实普通参考依据、明确冲突排除。
2. **正式历史先单老人，后多老人**，保持授权与历史不可变。
3. **后续以 B1.2.6 已验收工作区为优先起点**，先保留并核对另一主工程特有的正式历史后端实现。
4. **正式历史采取方案 A 显式保存**，用户需要主动确认保存，查看 Preview 不触发历史写入。
