## 1. Explicit completion operation

Budget completion validation and navigation to Profile continue to operate on the local Draft. They do not create a history record. POST `/api/v1/completed-assessments` is an explicit SAVE_COMPLETED_ASSESSMENT operation, exercised only by the isolated synthetic harness. No production UI save action is added. The backend checks authentication, request shape/version, full completion validation, and the current sole Elder binding before committing.

Request exact fields: `kind=completed_assessment_save_request_v1`, `intent=SAVE_COMPLETED_ASSESSMENT`, `assessmentContractVersion=assessment-schema-v2`, `schemaVersion=2`, `elderId`, `idempotencyKey`, `answers`. Unknown fields (including ownerUserId, id, localDraftId, completedAt, source or status) are rejected. A Draft envelope is not a save request. The request is bounded to 64 KiB. The existing `validateAssessmentAnswersV2(answers,true)` pure implementation is packaged and executed by a bounded Node 24 bridge; required, conditional, type, option-code and selection rules are not translated or changed. Invalid/unsupported input fails without persistence. Unavailable validator fails closed.

## 2. Trusted identity and Elder binding

Only the current C5 server resolver can provide owner userId. No test identity/header parser exists in main application code. Missing/expired/invalid sessions fail authentication; infrastructure failures remain unavailable/error. Write and list transactions revalidate C5 evidence and lock the sole binding through the existing transaction-scoped Elder repository. Unbound owners and caller elderId mismatches fail closed. No implicit Elder establishment, second Elder, shared owner or transfer is introduced.

The new history authorization is scoped to records whose ownerUserId AND elderId agree with this trusted current binding. Client userId/owner query parameters never choose scope. A cursor from another owner is invalid; guesses cannot disclose a record. The separately gated TEST_ONLY detail endpoint is specified in section 8.

## 3. Server record and immutable snapshot

Server-generated `id` is a UUID; `completedAt` is the server Clock instant truncated to microseconds. The stored CompletedAssessment V2 snapshot uses existing `kind`, `id`, `elderId`, `status=completed`, `schemaVersion=2`, `answers`, `completedAt`; snapshotRevision=1 identifies this immutable stored snapshot. `assessmentContractVersion=assessment-schema-v2` and source `COMPLETED_ASSESSMENT_HISTORY_TEST_ONLY_V1` are server-controlled history envelope metadata, not changes to Assessment semantics. Client timestamps/provenance never become server facts. Historical V1 is not migrated or newly created by this V1 save API.

Owner/elder relation, snapshot, SHA-256 payload digest and owner-scoped idempotency key are committed atomically. A transaction locking the current Elder binding serializes same-owner saves. Database primary key, unique(owner_user_id,idempotency_key), foreign keys, CHECKs and UPDATE/DELETE rejection triggers protect the TEST_ONLY immutable store. No mutation/reassessment API is exposed. Same owner/key and canonical payload returns the existing metadata; a different payload conflicts. Canonical object-key sorting retains array order. Failed validation/authorization/SQL rolls back; retries reuse the same key. A new explicit save with a new key creates a separate identity.

## 4. Minimum list projection and bounded pagination

GET `/api/v1/completed-assessments?limit=20&cursor=<last-id>` uses limit 1..50 and keyset order `(completed_at DESC,id DESC)` with binary ID collation. The cursor is an existing last-record ID resolved inside the trusted owner's current Elder scope; malformed/unowned/missing cursors return INVALID_CURSOR without identifying another account. No offset or client completion time controls the boundary. Inserts ahead of a cursor do not replay an earlier page.

Success envelope: `contractVersion=completed-assessment-history-api-v1`, `kind=completed_assessment_history_result_v1`, `availability=ready`, `items`, `nextCursor` (null or last returned ID). Each item has only `kind=completed_assessment`, `id`, `status=completed`, `schemaVersion`, `completedAt`, `assessmentContractVersion`, `source`, `snapshotRevision`. Lists never return ownerUserId, elderId, answers, health summaries, payload hashes or idempotency keys. Empty means authenticated successful scoped query with zero items. Authentication/permission failures are never empty.

POST success is a metadata-only `completed_assessment_save_result_v1` envelope, availability created/replayed. Safe failure codes/statuses: UNAVAILABLE/503 (feature/validator/auth infrastructure absent), UNAUTHENTICATED/401, FORBIDDEN/403 (binding), INVALID_INPUT or INVALID_CURSOR/400, IDEMPOTENCY_CONFLICT/409, ERROR/503 (technical failure). No raw exception, principal, session evidence or answers are logged/returned. Retry is explicit; no client write fallback.

## 5. Isolation and frontend state boundary

The isolated SQL migration is outside default `db/migration`. The main service is disabled by default. The frontend Provider uses existing C5 session acquisition and JSON auth headers, not Draft/Visit sources. Unconfigured/disabled -> UNAVAILABLE; authentication/permission failure -> ERROR with safe identity feedback; network/malformed/technical failure -> ERROR; only a validated ready envelope -> EMPTY/READY. List metadata is validated before projection; unsupported provenance cannot be relabeled TEST_ONLY/local. The new server source is displayed explicitly as TEST_ONLY isolated synthetic saved history. Read/write auth clients contain no bundled fixture. Normal unconfigured runtime retains UNAVAILABLE. There is no automatic save on Profile/Recommendation/show/navigation. Page lifetime prevents stale async responses updating a hidden/destroyed instance; bounded load-more has one action chain and no navigation/Draft side effects.

Before acquiring a C5 session the Provider reads public GET `/api/v1/completed-assessments/capability`: exact fields `contractVersion`, `kind=completed_assessment_history_capability_v1`, `availability=ready|unavailable`, `source`. ## 8. TEST_ONLY user loop (Owner-authorized proposal, not Frozen)

The additional server flag `assessment.history.user-loop-enabled=true` is default false and only effective inside the existing disposable History gate. GET `/api/v1/completed-assessments/user-loop-capability` returns contractVersion, kind `completed_assessment_user_loop_capability_v1`, availability ready/unavailable and the existing server TEST_ONLY source or null. Only a valid server response in a develop runtime enables the History page's separate TEST_ONLY operations. Query parameters, page data, testOnly declarations and debug headers cannot grant backend access or enable page handlers. Normal UI and existing navigation remain unchanged outside this branch. No synthetic login Provider enters main application code.

Explicit Save reads a validated complete local Draft only after this gate. It resolves (never implicitly establishes) the authenticated user's existing Elder binding, freezes a clone of answers plus an application-memory save intent and idempotency key scoped by backend origin and the server-authorized sole Elder binding, and calls the existing POST. Nothing writes/clears the Draft. Rapid taps share pending; ambiguous timeout/failure retains the exact key/payload. Editing during an unresolved intent cannot silently turn retry into a different save; retry uses the frozen intent, with visible feedback. Acknowledged server metadata alone permits success feedback. A subsequent explicitly confirmed independent AssessmentSession uses its own server-bound intent. Hidden/detached pages ignore late UI updates; a new History instance can reuse an unresolved intent only after resolving the same authorized Elder binding again; success never deletes local answers. Retry success explicitly identifies the original request; later edits in that same saved session remain unsaved and cannot silently create another completion. Acknowledged payload copies are discarded. Intent recovery after a full application cold restart is not implemented or approved for production; no new sensitive local persistence is introduced. Real phone authorization is not requested.

When the user-loop gate is enabled, newly created CompletedAssessment records atomically receive an independent immutable `historical_profile_display_v1` snapshot in the V2 TEST_ONLY migration table. Derivation occurs once at creation from the server-generated CompletedAssessment snapshot through the existing pure `deriveElderProfileV2` implementation; it never reads current Draft, Profile, Catalog or Recommendation. Its controlled projection is limited to care level, mobility, rehabilitation, food texture, swallowing concern and user-reported cognitive concern, preserving unknown/needs_confirmation language. No names, raw health/ADL answers, evidence IDs, userId or elderId are returned. Snapshot metadata includes assessmentId/completedAt, Assessment schema 2, Profile contract/ruleset versions and display snapshot version 1. This is a minimal historical Profile display, not a full Profile, and no Recommendation snapshot is fabricated. Existing raw snapshots, IDs and snapshotRevision=1 stay unchanged. The new table has unique Assessment FK and immutable UPDATE/DELETE triggers; no backfill is performed.

GET `/api/v1/completed-assessments/{id}` requires the user-loop gate, C5 transaction-scoped principal and sole Elder binding, then queries by owner+elder+id. Authenticated wrong-owner, absent and malformed IDs all return the same 404 NOT_FOUND without revealing existence. Detail success is an exact `completed_assessment_detail_v1` envelope with contractVersion, item metadata, profileAvailability ready/unavailable, profileDisplay object/null and recommendationAvailability=unavailable. Original answer snapshots are not in this DTO. Old records lacking the new display snapshot return legitimate profile unavailable; detail does not derive or migrate them. UI details are an inline, read-only view inside the existing History route, with explicit return-to-list and prior scroll restoration; no production route is added. Result reads/retries never invoke Recommendation or Draft derivation.

Safe reassessment checks the existing single-slot store only after the isolated gate. Under approved D03/D04, a trusted original-payload save acknowledgment, unchanged current answers and revalidated C5/Elder scope permit explicit confirmation and compare-and-replace into an independent empty session. Cancellation, modified answers, pending/unknown/recovery or missing cold-start proof preserve and block. An already valid empty V2 context can use the registered Intro route without clearing or copying answers. Intro's existing explicit start action and B01 capacity/Back rules remain authoritative. The current Session lifecycle section below defines durable candidate metadata, server association and CAS failure behavior; no multi-Draft migration/backup policy is introduced.

Bridge execution uses argument-vector ProcessBuilder, trusted packaged scripts, bounded stdin/stdout, local per-process streams, at most four concurrent child processes and an execution deadline including stdin writes. Missing runtime, child failure, timeout or invalid display refuses the entire create transaction; no sensitive payload is logged. Node 24 and the configured executable are declared dependencies. These controls serve the concrete bridge boundary, not an unrelated security refactor.
