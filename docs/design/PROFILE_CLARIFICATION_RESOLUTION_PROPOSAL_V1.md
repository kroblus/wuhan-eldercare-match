## 2. 方案的产品结果

在现有画像的每一项待确认事项旁提供“补充确认”，保留原来的“修改原回答”。用户不必反复重填六步问卷。

补充页面依次展示：原回答 → 具体需要确认的问题 → 回答者身份及信息来源 → 对本次结果的影响。保存后明确显示以下三种结果之一：

- **本项已补充确认**：满足新规则定义的证据条件；不等于整份画像或某家机构已通过。
- **已记录，仍需进一步确认**：资料已保存，但没有达到解除阻断的条件，并说明还缺什么。
- **原回答已变化，请重新确认**：本次补充不再适用于最新回答；不得沿用旧结论。

禁止使用单一“我已确认全部填写”复选框直接解除推荐阻断。保存成功、填写完整、风险存在、机构接收确认分别表达。

## 3. 三项分别需要补充什么

### 3.1 情绪波动：确认已观察到的行为，不推断诊断

原“情绪波动明显”保留。补问“除情绪波动外，是否观察到容易躁动或攻击行为？”，分别提供“已观察到”“未观察到”“不了解/无法确认”，并记录观察者角色及实际观察时段。这里仅收集与既有 `agitation / aggression` 相同范围的用户报告，不由系统评判危险程度。

来源优先为本人或实际照护者的直接观察；家属转述需标为转述。记录角色与来源类别，不要求真实姓名、电话或上传病历。未提供观察来源或无法确认时继续保留待确认。

拟议规则：可信来源类型、所需字段、冲突处理获 Owner 批准后，“已观察到”可形成明确的 reported risk；“未观察到”可形成限定于本次报告的 `not_reported`。两者均保留情绪波动原事实，不表示医学诊断或排除风险。现有明确躁动/攻击报告不能被一条相反补充静默覆盖；冲突仍需核对。

此映射只在新的画像规则版本内定义。明确 reported risk 后，沿用批准版本的安全匹配规则；不额外声称机构具有未经核验的行为照护能力。

### 3.2 吞咽：记录具体照护信息，用户确认不能证明机构能接收

原“偶尔吞咽不顺或容易呛咳”保留，不改成“正常”，不推导鼻饲或照护等级。

补充内容限定为事实记录：由谁观察、观察时段、是否已有专业评估或现行照护安排、是否了解当前执行的进食协助安排。不了解可明确选择“不清楚”。本方案不定义医疗分级、饮食处方或临床判断阈值。

必须区分三种来源：用户/照护者观察、用户转述已有专业安排、将来经合法流程核实的专业或机构接收记录。家属选择“已有评估”只能保存为用户转述，不能生成 verified 专业结论，也不能改变机构核验状态。

**第一步建议交付**：将上述资料保存为“已记录，待进一步确认”，保留现行推荐阻断；允许继续浏览机构目录并查看公开详情，在清楚标识的“待机构评估”流程中携带最小必要信息。不能把目录改名为“推荐机构”或默认选中匹配机构。

**未来如需解除吞咽阻断**：必须另行批准可审计的个案接收/照护确认协议。建议独立于 Institution 通用事实，绑定本次需求快照、机构稳定身份、机构 revision、核实来源、适用照护安排及有效性。来源授权、有效期、撤回、照护安排变化后的失效规则，均须在 successor Contract 中明确，未定义前不得启用。仅“已联系”“已读”“家属同意”均不足以通过。

当前软食/特殊处理饮食属于展示信息，不能拿其 available 证明吞咽风险已被承接。新协议未经批准或未取得有效资料时，仍不能保证有推荐卡。

### 3.3 认知症专区：区分明确需要、家庭偏好与尚未确定

保留走失风险事实。补问“是否已经明确需要认知症专区？”，提供“明确需要”“目前未确定”“家庭暂不要求专区”，解释该问题不是认知症诊断。

- “明确需要”：应引导到已有特殊护理题选择真实需求；保持当前 direct requirement 优先规则。由用户确认实际修改，不自动写入原问卷或旧快照。
- “目前未确定”：仍保留待确认。
- “家庭暂不要求专区”：仅表示家庭意向，不能据此消除风险线索或自动生成 `not_required`。如未来允许“专业确认不需要专区”解除本项，须先定义可接受的真实来源及核验流程；当前不冒充已具备该能力。

无论专区需求如何，已有走失风险及机构走失支持要求不消失，不能用专区选择替代另一项安全要求。

## 4. 数据与版本边界

补充确认拟作为独立、版本化记录，关联原评估/画像，不新增或重命名原有 27 个稳定题目 ID，不改变必填/选填与选项语义。

最小记录应包括：记录版本、对应评估与画像版本、原答案/画像关联摘要、目标待确认项、结构化回答、回答者角色、来源类别、观察时段、记录时间及被替代记录引用。服务端核验时间、权威来源或有效期只能在真实具备相应流程后产生，不能用本地时间冒充。

- 新补充采用追加版本，不就地覆盖 CompletedAssessment、旧 ElderProfile、旧 Recommendation 或 Institution revision。
- 只读历史结果仍使用保存的当次快照。补充后需显式“生成新的评估结果”，新旧结果分别可查；保存新快照的身份、准入和持久化规则在实施前明确，不给旧快照补写新语义。
- 必须绑定相关原答案：相关答案变化、身份不匹配、记录版本不支持或证据失效时，旧补充不再用于当前推导。无关展示偏好变化不得伪装成风险答案变化，具体绑定集合需有确定性规则。
- 新 evidence source 只能由 successor validator 接受。现有 V2 validator 会从原答案重放推导，不允许 UI 自行把 needs_confirmation 改成 known 或删除 clarification。
- Preview 与正式路径必须重放相同输入及版本，不能只在 Demo 或页面上放宽。
- 不在日志中输出完整健康答案、画像或补充文本。未授权外部存储、网络、病历上传或联系操作，不借本方案启用。

版本号需在正式 Contract 起草时根据届时索引分配，本文件不预占或宣布 V3 已生效。旧 V2 持续可重放。

不修改 Recommendation V2 的既有排序、不回写 Institution verification，不使用 VisitEvaluation/顾问回复/AI 文字充当安全证据。真正改变准入时使用明确的后继版本及新结果快照，保留旧行为。

## 6. 必须覆盖的验收

1. 三项截图风险在 V2 仍得到原有 3 项阻断；同答重提结果确定不变。
2. 新页面允许“无法确认”，不会自动选择否、正常或不需要。
3. 情绪波动保留；补充行为回答有真实来源引用，冲突不被静默消除。
4. 吞咽困难不映射为正常、鼻饲或软食已能安全承接；用户转述不产生 verified。
5. 明确专区需求仅消除自己的线索待确认，不抹除走失支持、行为或吞咽项。
6. 原答案变化、错绑评估/机构、旧 revision、不支持版本、失效或撤回证据均不能放行。
7. 新旧结果均可查询；旧快照与推荐顺序不被重算或就地升级。
8. 返回、再次进入、保存失败重试、连续点击与草稿恢复正常；320/375/430px 和大字号可操作。
9. Demo 使用显式合成来源并保持外部副作用隔离；Production 无合成确认、无默认 verified、无测试解锁入口。
10. 自动化、DevTools 与 Owner 真机证据分别记录。上述新流程目前全部未实施、未验收。
