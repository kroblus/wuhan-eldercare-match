## 1. 结论及约束

Owner 已确认：

1. 老人关键风险明确、机构关键护理能力全部未知时，**仍允许作为严格标识的初步参考候选**；前提是存在其他真实参考依据、没有已知明确关键冲突，且绝不作能力或接收承诺。
2. 正式历史记录**先实现当前已授权单老人的完整闭环**，多老人历史在后继阶段扩展。
3. 后续工程整合**优先从 B1.2.6 已验收工作区启动**；不得假设另一主工程的服务端历史能力已经在该分支可用。
4. 正式历史采用**方案 A：用户显式点击保存**，仅查看评估或推荐 Preview 不触发正式写入。

本稿定义上述决策在领域模型、状态机、持久化、页面集成和测试中的最低约束。**C1 专属标识和机器规则以独立《INITIAL_REFERENCE_RECOMMENDATION_CONTRACT_V1_3_C1》为准**；本文其它 C2 英文标识仍为候选协议用语，不代表现有代码字段。2026-10-26 的 Codex《V1_3_CODEBASE_COMPATIBILITY_AUDIT》及《V1_3_C1_REFERENCE_TECH_CONTRACT_REVIEW》已完成只读技术核查。Owner 同日追加确认最低可信普通依据和“核实型优先、不补数”两个产品细则，并于本轮进一步确认 C1 技术方案（含两条 C1 饮食明确冲突否决）。**C1 技术规则已冻结，但代码、测试和 C2 后端均尚未获实施授权／完成。**

**不改变的边界**：原始用户答案真实；已有 Exact、SoftNear、Conditional 和明确不适配规则；未核实事实不能表述为已核实；历史快照不可变；账号／老人访问控制；匿名 Preview 不伪装成正式历史；Demo 与 Production 隔离。

## 3. ElderProfile 后继契约

### 3.1 不混淆的四个维度

| 维度 | 候选状态 | 语义 |
|---|---|---|
| 问卷完整性 | `complete`、`incomplete` | 只根据现有 Assessment 必填和条件规则；合法 `unknown` 不等于遗漏 |
| 已报告的事实 | `reported`、`not_reported`、`unknown` | 不修改用户原答案；未知是事实不确定而非“正常” |
| 补充确认 | `not_needed`、`needs_more_information`、`provided`、`cannot_confirm_now` | 是否有补充事实、来源和处理说明；用户无法确认不是错误答案 |
| 机构接收相关核实 | `not_applicable`、`pending_institution`、`verified_fact_available` | 这里只记录核实需要和已有证据；**不输出入住许可或医疗诊断** |

这些名称不是新增 Assessment 选项。任何写入补充信息的功能都必须有独立版本化字段，不能暗自把 `unknown` 写回已有题目 ID。

### 3.2 三项事实关系

- **情绪波动**：用户报告 `mood_instability` 只能证明报告了情绪变化，不足以自动推导攻击行为或躁动。可以保留行为风险待核实，但不能据此抹去整个参考通道。
- **吞咽不顺**：保持已有吞咽／饮食风险记录；平台不得从用户描述推定机构能提供相应护理。风险明确但能力未知可进入**受限参考**，每张相关卡要列出待机构核实事项。
- **走失风险与认知症专区**：独立表示风险与居住专区意向。走失风险不能自动写成“必须认知症专区”；如缺少显式确认方式，须在后继版本提供合法的澄清语义，而不是逼迫返回原题更改事实。

### 3.3 Readiness 拆分

必须区别：

- 旧 `elderReadiness`／`required_before_hard_filter`：**原 V2 已核实匹配的阻断机制保留**，用于旧语义回归。
- 新“参考信息可展示资格”：问卷按当前规则完整、老人风险事实保留、存在可信普通参考依据，即使某些风险待机构核实，仍**可以**进入参考候选通道。

不能简单将旧 `elderReadiness` 置为 ready；也不能将所有 `clarification` 直接删掉。推荐引擎需要显式接收二者并输出不同类别。

## 4. 机构事实和核验后继要求

### 4.1 至少区分两个核验层次

| 层次 | 允许用于哪类展示 | 风险 |
|---|---|---|
| 机构主体与基本目录信息 | 经过现有目录真实性与来源 Gate 后才可用于正式参考 | 实体、机构地址等身份或来源不可信时不得伪造候选 |
| 具体护理能力 | 只有存在对应的有效证据，才可宣称提供某项支持 | `unknown`、过期、未核验、矛盾不得提升为 `verified_support` |

本次**允许“主体资料合格、护理能力未知”**进入受限参考通道，不等于允许虚构真实机构或绕过整体资料合法性验证。

### 4.2 事实证据最低要素

后继实现如需新增字段，应以现有 Institution Contract 为基础，而不是另立与旧字段冲突的第二套真相源。建议每项参与匹配的事实都有：`value`、`verificationState`、`sourceKind`、`observedAt`、`validUntil`（如适用）及对应机构版本或快照引用。

缺证据时输出未知；已知能力明确不满足时为明确冲突，必须从该老人个性化候选排除。目录数据一条非法引发整池失败（AUD-09）是否改造为上游隔离，不在本次推荐领域逻辑中擅自改变。

## 5. Recommendation 后继契约

### 5.1 三个输出通道必须互斥

1. **核实型匹配**：沿用旧 Exact／SoftNear／Conditional 及其事实、排序和安全条件；未知机构关键能力不会因为新产品定位而混入旧通道。
2. **初步参考候选**：新类别。允许关键风险已明确、机构相关能力完全未知，但只能使用其他可证实的普通参考条件形成理由，不输出“关键护理支持已满足”。
3. **公开机构目录浏览**：没有足够个性化依据时的独立浏览入口，不计入推荐卡和匹配率。

同一个机构在同一次结果中不得同时作为“已核实符合”和“初步参考”重复出现。若信息已足以进入更强的旧类别，应按旧规则输出并保留其真实条件说明。

### 5.2 初步参考候选准入判定

| 检查项 | 必须满足 | 失败后的行为 |
|---|---|---|
| 完成度 | 现行问卷按条件规则完成 | 不输出个性化候选，提示继续填写 |
| 机构主体 | 满足现行可供正式目录使用的主体与来源校验 | 不输出为正式个性化候选 |
| 可信参考依据 | 至少一项真正与该老人需求关联的可核实普通条件，如指定区域匹配、费用范围重叠、已核实基本收护范围 | 仅提供普通目录入口，不使用“推荐”措辞 |
| 关键冲突 | **不存在明确已知不能满足的关键条件** | 从该老人的个性化匹配和参考通道排除 |
| 机构关键护理能力 | 可以 `unknown`、未核验或过期待核实，**不要求先取得个案接收确认** | 保留未知状态并显著展示；绝不提升为已满足 |
| 可解释性 | 输出已知依据、逐项待核实风险、来源与下一步动作 | 不生成无依据卡片 |

特别说明：单有机构名称和地址，不构成“已知普通需求条件匹配”。候选准入需要**机构事实与某项真实用户需求有可解释的对应关系**。不得通过人工固定推荐顺序、隐藏风险或伪造机构能力填补候选池。

### 5.3 决策顺序

1. 根据稳定的 Assessment → ElderProfile 生成已知事实和风险。
2. 依既有规则运行核实型匹配，记录 Exact／SoftNear／Conditional 等状态。
3. **仅当旧 V2 没有任何可展示的 Exact／SoftNear／Conditional 时**，才对没有明确关键冲突的机构独立判定初步参考准入；不能把旧 V2 的 `blocked`、`null`、`UNVERIFIED` 直接转成参考资格。
4. 旧 V2 有卡则原组原序原数量；否则只展示通过新准入的参考机构，按独立的依据类别数排序，仍遵守**最多三家**；不混组、不强行补足三家。
5. 若没有可解释个性化候选，输出明确空结果或目录浏览引导；不得暗示“全武汉都不适合”。

不设旧类型与新参考之间的加权分数；采用**旧可展示组优先，否则新参考，否则合法目录入口**的组合策略。新参考内部才按独立类别数和稳定机构 ID 排序。该规则已获 Owner 确认；正式冻结口径见独立 C1 契约，本文 §9.0A 记录技术评审来源与原始建议。

### 5.3A 产品层已确认、实现细节待技术审查的展示与排序规则

**适用范围仅为新增 V1.3 composition**，不得改变冻结 V2 的内部排序与原始语义。

1. 先计算旧 V2 的合法核实型卡及 Conditional。若已存在可展示的旧卡，只按原组规则输出，不混入低一层初步参考“凑三家”。
2. 若没有可展示的旧卡，才对其他合法目录机构执行初步参考资格评估。必须同时满足：问卷按 32／26 及条件规则完成、主体目录合法、无已知明确关键冲突、至少一项与老人**明确需求**对应的当前可信普通事实。
3. 普通事实白名单候选为：老人指定区域与合法机构区划匹配；收费区间与用户预算有可比口径的实际重叠；与老人明确偏好相应的已核验普通服务／收护类别。**只有机构位于武汉、具备名称和地址、存在 VR 或收费字段却无有效范围，不构成个性化依据。**
4. 初步参考按独立的有效依据类别数降序排序，相同数量按稳定 institutionId 升序；不借用冻结 V2 排名权重、不拿护理未知加分。候选去重键为 institutionId，展示保留精确 recordRevision；任何时候个性化机构合计不超过三家。
5. 参考来源有错误、不可用或无可比证据时，该项普通依据不计入；不存在其它有效依据则降级为合法机构目录浏览。已知关键能力 unsupported 的机构，即使地域和预算都匹配，也不能成为该老人个性化参考。
6. 对老人侧所有待澄清风险及机构能力逐项保留：reported/unknown/needs_confirmation 和 unknown/unverified/expired/unsupported 不能合并成一个布尔“支持”。referenceReasons、referenceWarnings 与来源证据均随结果快照保存。

其中第 1–3、5 条的产品准入与展示边界已由 Owner 确认；第 4 条中同分按 institutionId、依据计数和精确指针等属于**技术实现建议**，须用固定测试向量验证。此处不等于已冻结到代码。

### 5.3B 建议的用户可见组合状态

| 概念状态（候选名） | 适用情况 | 必须与之区分 |
|---|---|---|
| VERIFIED_OR_CONDITIONAL_RESULTS | 至少存在旧 V2 可展示候选 | 继续保留每张卡真实 tier，不将 Conditional 说成无条件满足 |
| INITIAL_REFERENCE_ONLY | 没有旧核实型卡，但有一至三家合法初步参考 | 旧 V2 内部仍可能为 no_safe_recommendation / UNVERIFIED |
| NO_PERSONALIZED_CANDIDATE | 两个通道均无合法个性化候选 | 合法普通目录仍可独立浏览 |
| DATA_OR_SERVICE_ERROR | 目录版本、来源、身份或系统调用异常 | 不将技术失败包装成“不适合入住” |

必须同时保留旧引擎的原始状态字段与 V1.3 用户可见组合状态，禁止反向修改旧 no_safe_recommendation 的真实含义。

### 5.5 UI 不可退让的要求

- 参考候选首屏可见“初步参考 · 关键护理能力待核实”，风险说明不能只在悬浮提示或折叠底部。

## 6. 正式单老人 History 后继契约

### 6.1 状态机

| 状态 | 允许操作 | 禁止误报 |
|---|---|---|
| `preview_only` | 浏览临时画像和推荐 | “已经保存” |
| `needs_identity_or_elder_binding` | 引导合法登录或绑定当前老人 | 将匿名 Preview 直接提升为正式历史 |
| `saving` | 明确请求保存；防连续点击重复提交 | 重复创建独立历史记录 |
| `saved` | 展示时间、回执与历史入口 | 将本地 Demo 会话当作跨设备持久化 |
| `save_failed_retryable` | 在安全条件下重试 | 页面仅提示成功、后台实际失败 |
| `historical_read_only` | 读取已保存快照 | 使用最新问卷或机构目录改写过去 |
| `history_unavailable_or_unsupported` | 解释未开放、无权限、快照缺失或版本不支持 | 静默空白、虚构新推荐 |

### 6.2 保存触发和数据一致性

**Owner 已确认采用显式保存（方案 A）**：只有用户点击“保存本次评估”且完成必要身份、当前老人关联和快照一致性检查，才发起正式保存。单纯进入推荐页面不会自动产生历史记录。接口返回成功前不得显示“已保存”；保存失败须保留重试能力并避免重复记录。

保存对象应有可复核的绑定关系：`owner`、`elder`、`assessmentId/version`、完整答卷快照或可信引用、画像版本、推荐版本、结果状态、候选及其来源版本、推荐理由与差异、核实状态、保存时刻。保存无个性化候选时也要记录“零候选及其原因”，不可据此拒绝保存。

保存必须有服务端幂等或等效的可靠去重语义；从页面连续点击或网络重试不应生成重复记录。失败不能误报成功。保存前后若账号、老人或评估快照发生变化，应阻止错绑和陈旧结果入库。

### 6.2A 正式手动保存的状态转换与不可逆边界

| 当前状态 | 事件 | 允许转换或结果 |
|---|---|---|
| preview_only | 仅进入画像、推荐、刷新结果或退出 | 仍为 preview_only；零正式持久化 |
| preview_only | 用户明确点击保存，尚无可信身份或合法老人绑定 | needs_identity_or_elder_binding；引导授权，不伪造保存成功 |
| preview_only / needs_identity_or_elder_binding | 完成合法授权并再次确认保存 | saving；固定本次答案与呈现结果的版本／来源摘要 |
| saving | 服务端发现当前 Catalog、规则或结果与用户看到的不一致 | 进入需重新展示与确认的非成功状态；不得静默存另一结果 |
| saving | 有效成功回执且账号／老人／请求摘要匹配 | saved；可打开正式历史 |
| saving | 网络超时或回执丢失 | 状态未决，查询同一幂等意图；不得自动生成新 key |
| saved | 用户修改原答卷或发起重新评估 | 保持旧记录不可变，新变化显式为未保存；另存生成新记录 |

**敏感数据最小写入原则**：匿名 Preview 和草稿不得因推荐页 onShow、自动重算或“查询核验结果”而在正式服务器提前创建完整健康记录。持久化只在用户显式动作、适当信息告知、可信身份/老人授权及一致性校验之后进行；身份或后端接口若要求额外的法定处理依据，应在正式上线前另行确认。

**服务端验证原则**：客户端传来的用户／老人标识只能作请求线索，权威 owner 与 elder 必须从可信会话和服务端合法绑定解析。正式 assessmentId/completedAt 由服务器生成；预览 evaluationAsOf 单独保留；未知来源或不受支持版本不得被强制按旧 schema 解析。

建议为正式 History API 固定以下概念性错误语义：AUTH_REQUIRED、ELDER_BINDING_REQUIRED、FORBIDDEN、SNAPSHOT_CHANGED_RECONFIRM、IDEMPOTENCY_CONFLICT、SAVE_OUTCOME_UNKNOWN_RETRY_LOOKUP、UNSUPPORTED_SNAPSHOT_VERSION、SERVICE_UNAVAILABLE。这些代码名仅为设计候选，不是目前可用接口。

### 6.3 查询与不可变性

- 首期只允许当前账号有权访问的**一位当前已绑定老人**的历史；切换到其他老人需合法的后续权限和产品设计，不删除既有 owner + elder 校验。
- 历史按时间倒序，能查看当次结果，即使当次无候选也能显示原因。
- 旧记录没有推荐快照时应显示“该次未保存推荐结果”；不得使用当前目录补算。
- 旧记录版本不支持时保留原数据并展示可解释的只读状态；与认证失败、空记录、资料暂不可用区别处理。
- 机构资料更新不能改变已保存的推荐快照。若当次完整机构详情并未保存，不可伪称“查看当时详情”；另提供“查看机构当前资料”。
- 必须通过真实 HTTP、数据库事务及重启/跨设备验证。TEST ONLY 后端、会话内存和模拟 API 无法证明正式功能已开放。

### 6.4 实施基线审查后必须补齐的正式工程事实

Codex 当前源码报告已证实：B1.2.6 工作区无 server/，原主工程有严格隔离的 TEST ONLY HistoryService/Repository/SQL；两者并非连续 Git 历史。正式历史必须明确后端部署归属、Production 来源标识、真实 C5 principal 与老人绑定入口、数据保留期限／访问控制、正式 SQL 版本迁移及回滚方案。不可通过关闭 TEST ONLY guard 达成。

前端 History client 和 user-loop 代码在 B1.2.6 已存在，但普通构建保存 Gate 为关闭状态，不能将源码存在等同功能已开放。当前历史 reader 严格按旧版本／source 检查，新参考类别应引入新 reader 分发，保留旧快照，不在读取时用当前目录重算。

#### 输入快照及信任边界

| 输入 | 使用要求 |
|---|---|
| 完整 Assessment V2 | 使用当前 32 题、26 必填及条件规则；合法 unknown 不等于漏答；不新增问题 |

#### 资格判断必须全部通过

1. 问卷 complete，且来源及机构主体合法；资料错误属于技术失败，不是“老人无合适机构”。
2. 存在**至少一类**与用户明确需求对应的可信普通依据，限于：指定区域匹配、口径可比较的月费用区间实际重叠、已核验普通服务／收护偏好匹配。
3. 机构对老人确实需要的关键能力，不存在有时效、来源和机构版本证据支持的明确 unsupported。此项必须从已有 Hard Filter 的事实／冲突证据提取，不能仅凭旧 matchTier=null 或 UNVERIFIED 推断无冲突。
4. 风险、澄清及能力 unknown 不被改成 ready／supported；但**在以上条件成立时不构成新参考通道的全局阻断**。
5. 不得把“机构存在”“位于武汉”“有照片/VR”“顾问愿意联系”等当作个性化参考依据。

#### 三类普通依据的判定细则

| 类别 | 建议机器判定 | 应排除的情况 |
|---|---|---|
| AREA | 用户确实表达当前有效的区域偏好；当前合法机构区域与之匹配 | 用户未选区域，或仅由默认城市/机构名称推断 |
| BUDGET | 用户预算与机构明确可比口径的月费用区间有交集；两个闭区间重叠可按 max(下限) <= min(上限) 判断 | 价格无来源、已失效、仅有首月价却无法与月预算比较，或缺失边界 |
| BASIC_SERVICE | 用户明确普通服务／收护偏好，机构同一项当前有有效的正面核验事实 | 未核实、过期、只是机构宣传文字；护理能力 unknown 不算正面事实 |

同一个类别至多算一项。价格重叠只说明预算可参考，不证明最终费用或床位可用。若目录字段目前无法表达来源有效性，应先选择缺省不计入，不得用常量/Mock 凭空补证据。

#### 结果组合与确定性

1. 旧 V2 先按原顺序计算和输出。若有可展示的旧卡，**只展示旧卡**，不混入初步参考补满三家。
2. 否则遍历同一合法 Catalog，独立计算新参考资格；不能直接把旧 candidateEvaluations 的 null/UNVERIFIED 全部显示成卡。
3. 新参考卡按有效普通依据类别数量降序，同分采用稳定 institutionId 升序；这只是可供测试的技术排序方案，不能解释为护理安全排序。
4. 同一 institutionId 在一个结果中只出现一次；引用精确 recordRevision，拒绝同一机构的矛盾 currentPointer；总量最多三家。来源数组任意置换不改变输出。
5. 新组合结果状态建议至少区分：旧候选可见、仅初步参考、无个性化候选、技术或来源错误；**同时保留旧 V2 的原始 no_safe_recommendation 和 blocked 事实**。
6. 单个新参考卡最小快照应包含：机构 identity/revision、依据类别与事实来源、老人实际风险／待澄清项、护理能力未知或已过期清单、待机构核实问题、policyVersion、datasetVersion、evaluationAsOf 和展示顺序。不得写入“机构已确认接收”。
